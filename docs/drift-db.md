# Drift in a Nutshell

This is a compact practical guide for using Drift in Flutter or Dart apps.
It is meant to be a quick reference: enough to understand the important parts, remember the common workflow, and copy the patterns you use most often.

## What Drift is

Drift is a Dart library for working with SQLite using typed Dart APIs.
It gives you:

- typed table definitions
- generated query helpers
- compile-time checks for many database mistakes
- a nicer API than writing raw SQL for everything
- the option to still use SQL when needed

In daily use, Drift is mainly about four things:

1. defining tables
2. generating code
3. reading and writing rows
4. organizing database code cleanly

## The 20% that covers 80% of usage

Most of the time, you only need to know how to:

- define a table
- register it in a database
- run code generation
- insert a row
- get rows
- update a row
- delete a row
- filter rows with `where`
- sort rows with `orderBy`
- use `Companion` and `Value(...)`
- model parent-child relations with foreign keys

If you are comfortable with those, you can build most CRUD features.

## The basic shape of Drift code

A minimal Drift setup usually looks like this:

```dart
import 'package:drift/drift.dart';

part 'app_database.g.dart';

class Todos extends Table {
  TextColumn get id => text()();
  TextColumn get title => text()();
  BoolColumn get isDone => boolean().withDefault(const Constant(false))();
  DateTimeColumn get createdAt => dateTime()();

  @override
  Set<Column> get primaryKey => {id};
}

@DriftDatabase(tables: [Todos])
class AppDatabase extends _$AppDatabase {
  AppDatabase(super.executor);

  @override
  int get schemaVersion => 1;
}
```

This already shows the main pieces:

- a table class extending `Table`
- a generated file with `part '...g.dart'`
- a database class annotated with `@DriftDatabase`
- a schema version

## How to think about the pieces

### Table

A `Table` defines the database schema for one type of row.
You describe columns, types, nullability, defaults, and keys.

### Database class

The database class collects tables and gives you query access.
This is the entry point for reading and writing.

### Generated file

Drift generates helper code based on your tables and database class.
You do not edit this file by hand.

### Companion

Each table gets a generated companion type.
You use it mostly for inserts and updates.

## Column types you will use most

These are the common ones:

- `text()` for ids, titles, names, notes
- `integer()` for counts, durations, status codes
- `real()` for decimal-like values
- `boolean()` for true/false flags
- `dateTime()` for timestamps and dates
- `blob()` for bytes

Examples:

```dart
TextColumn get title => text()();
IntColumn get count => integer()();
RealColumn get price => real()();
BoolColumn get isDone => boolean()();
DateTimeColumn get createdAt => dateTime()();
TextColumn get note => text().nullable()();
```

## Common modifiers

### `.nullable()`

Use this when a value is optional.

```dart
TextColumn get description => text().nullable()();
```

### `.withDefault(...)`

Use this for simple default values.

```dart
BoolColumn get isDone => boolean().withDefault(const Constant(false))();
IntColumn get count => integer().withDefault(const Constant(0))();
```

### `.references(...)`

Use this for foreign keys.

```dart
TextColumn get userId => text().references(Users, #id)();
```

### `.unique()`

Use this when a value must be unique.

```dart
TextColumn get email => text().unique()();
```

## Primary key patterns

You will usually use one of these two.

### Manual string id

```dart
TextColumn get id => text()();

@Override
Set<Column> get primaryKey => {id};
```

Use this when the app or backend creates ids.

### Auto-increment integer id

```dart
IntColumn get id => integer().autoIncrement()();
```

Use this when the database should assign ids automatically.

## Step-by-step: adding a new table

Suppose you want a task table.

```dart
class Tasks extends Table {
  TextColumn get id => text()();
  TextColumn get title => text()();
  TextColumn get description => text().nullable()();
  BoolColumn get isDone => boolean().withDefault(const Constant(false))();
  DateTimeColumn get dueDate => dateTime().nullable()();

  @override
  Set<Column> get primaryKey => {id};
}
```

Then register it:

```dart
@DriftDatabase(tables: [Tasks])
class AppDatabase extends _$AppDatabase {
  AppDatabase(super.executor);

  @override
  int get schemaVersion => 1;
}
```

Then generate code.

## Code generation

After changing table definitions or database annotations, run:

```bash
flutter pub run build_runner build --delete-conflicting-outputs
```

You usually rerun this after changing:

- a table
- a column name
- a column type
- a nullable rule
- a default value
- the `@DriftDatabase` annotation
- a DAO annotation
- the schema version

If Drift types look stale or missing, code generation is the first thing to check.

## CRUD you should memorize

Assume the database exposes a `tasks` table.

## Insert

```dart
await into(tasks).insert(
  TasksCompanion.insert(
    id: 'task-1',
    title: 'Buy groceries',
    description: const Value('Milk and eggs'),
    dueDate: Value(DateTime.now().add(const Duration(days: 1))),
  ),
);
```

## Read all rows

```dart
final rows = await select(tasks).get();
```

## Read one row by id

```dart
final row = await (select(tasks)..where((t) => t.id.equals(id))).getSingle();
```

If the row may not exist:

```dart
final row = await (select(tasks)..where((t) => t.id.equals(id))).getSingleOrNull();
```

## Update a row

```dart
await (update(tasks)..where((t) => t.id.equals(id))).write(
  TasksCompanion(
    title: const Value('Buy groceries and bread'),
    isDone: const Value(true),
  ),
);
```

## Delete a row

```dart
await (delete(tasks)..where((t) => t.id.equals(id))).go();
```

That small set already covers a lot of app work.

## Filtering rows

`where(...)` is one of the most used parts of Drift.

Examples:

```dart
final openTasks = await (select(tasks)
      ..where((t) => t.isDone.equals(false)))
    .get();
```

```dart
final urgentTasks = await (select(tasks)
      ..where((t) => t.title.like('%urgent%')))
    .get();
```

```dart
final tasksForUser = await (select(tasks)
      ..where((t) => t.userId.equals(userId)))
    .get();
```

## Sorting rows

`orderBy(...)` is another thing you use constantly.

Ascending:

```dart
final rows = await (select(tasks)
      ..orderBy([(t) => OrderingTerm.asc(t.title)]))
    .get();
```

Descending:

```dart
final rows = await (select(tasks)
      ..orderBy([(t) => OrderingTerm.desc(t.createdAt)]))
    .get();
```

Filter and sort together:

```dart
final rows = await (select(tasks)
      ..where((t) => t.isDone.equals(false))
      ..orderBy([(t) => OrderingTerm.asc(t.dueDate)]))
    .get();
```

## The important idea: `Companion` and `Value(...)`

This is one of the most important Drift concepts to understand well.

### Why companion classes exist

When inserting or updating, you often do not want to pass every field the same way.
Some fields are required, some are optional, and some should be left unchanged.

Drift solves this with companion classes.

For a `Tasks` table, Drift generates `TasksCompanion`.

### Insert example

```dart
TasksCompanion.insert(
  id: 'task-1',
  title: 'Read book',
)
```

### Update example

```dart
TasksCompanion(
  title: const Value('Read more books'),
)
```

### Why `Value(...)` matters

For updates, Drift needs to know the difference between:

- set this field to a value
- set this field to null
- do not touch this field

That is why `Value(...)` exists.

### `Value('something')`

Means: write this value.

```dart
TasksCompanion(
  title: const Value('New title'),
)
```

### `Value(null)`

If the field is nullable, this means: write null.

```dart
TasksCompanion(
  description: const Value(null),
)
```

### `Value.absent()`

Means: do not update this field at all.

```dart
TasksCompanion(
  title: const Value('Updated title'),
  description: const Value.absent(),
)
```

This distinction is very important.
A lot of confusion in Drift disappears once this clicks.

## Parent-child relationships with foreign keys

A very common case is one table belonging to another.
For example, tasks belonging to a project.

```dart
class Projects extends Table {
  TextColumn get id => text()();
  TextColumn get name => text()();

  @override
  Set<Column> get primaryKey => {id};
}

class Tasks extends Table {
  TextColumn get id => text()();
  TextColumn get projectId => text().references(Projects, #id)();
  TextColumn get title => text()();

  @override
  Set<Column> get primaryKey => {id};
}
```

Then a common query is:

```dart
final rows = await (select(tasks)
      ..where((t) => t.projectId.equals(projectId)))
    .get();
```

This pattern covers a lot of apps:

- posts and comments
- projects and tasks
- devices and logs
- users and addresses

## Joins: what they are for

You use joins when you need data from multiple related tables in one query.

Example idea:

- `tasks`
- `projects`
- fetch tasks together with project info

A typical join looks like this:

```dart
final query = select(tasks).join([
  innerJoin(projects, projects.id.equalsExp(tasks.projectId)),
]);

final rows = await query.get();
```

Then you read each joined row:

```dart
for (final row in rows) {
  final task = row.readTable(tasks);
  final project = row.readTable(projects);
}
```

You do not need joins every day, but they are worth recognizing.

## Watching data reactively

Drift can stream query results, not just fetch once.
This is useful for live UI updates.

Example:

```dart
Stream<List<Task>> watchOpenTasks() {
  return (select(tasks)..where((t) => t.isDone.equals(false))).watch();
}
```

Use `.get()` for one-time fetches.
Use `.watch()` when the UI should react automatically to DB changes.

## Organizing Drift code well

A good habit is to keep raw database code grouped together.
Do not scatter queries randomly across the app.

Common approaches:

- one database class with helper methods
- DAOs for grouped query logic
- repository classes on top of Drift

The exact architecture can vary, but the key idea is the same:
keep table definitions, queries, and mapping understandable.

## A simple DAO example

```dart
class TaskDao {
  final AppDatabase db;

  TaskDao(this.db);

  Future<List<Task>> getAllTasks() {
    return db.select(db.tasks).get();
  }

  Future<Task?> getTaskById(String id) {
    return (db.select(db.tasks)..where((t) => t.id.equals(id))).getSingleOrNull();
  }

  Future<void> insertTask(TasksCompanion task) {
    return db.into(db.tasks).insert(task);
  }

  Future<void> deleteTask(String id) {
    return (db.delete(db.tasks)..where((t) => t.id.equals(id))).go();
  }
}
```

This keeps the rest of the app from needing to know Drift details.

## Migrations: the nutshell version

When the structure of the database changes, that is a schema change.
Examples:

- adding a table
- removing a table
- adding a column
- renaming a column
- changing a column type

When that happens, you usually need to:

1. update the table definition
2. bump `schemaVersion`
3. define migration logic if existing installed databases must be preserved

Example:

```dart
@Override
int get schemaVersion => 2;
```

Early in development, people often reset local data and move on.
In real apps with existing user data, migrations become very important.

So the practical rule is:

- if data does not matter yet, schema changes are easy
- if users already have local data, handle migrations carefully

## Common mistakes

### Forgetting code generation

If generated types are missing or old, rerun:

```bash
flutter pub run build_runner build --delete-conflicting-outputs
```

### Editing generated files

Never hand-edit `*.g.dart` files.

### Misunderstanding `Value(...)`

Remember the difference between:

- `Value(x)`
- `Value(null)`
- `Value.absent()`

### Nullable mismatch

If the column is nullable, your Dart usage should reflect that.
If it is non-nullable, do not treat it as optional.

### No foreign key for related data

If rows clearly belong to a parent, model that relationship properly.

### Scattered queries

If database code is everywhere, it becomes hard to maintain.
Group it.

## A go-to checklist for adding a table

```text
1. Define the table
2. Choose the primary key strategy
3. Add nullable/default/foreign-key rules
4. Register the table in the database
5. Run code generation
6. Add insert/read/update/delete queries
7. Add filter/sort queries if needed
8. Bump schemaVersion if the schema changed
9. Test the whole flow
```

## A go-to checklist for adding related tables

```text
1. Create the parent table
2. Add the child table
3. Add a foreign key from child to parent
4. Run code generation
5. Add query methods for loading children by parent id
6. Add write methods for insert/update/delete
7. Test with real linked data
```

## What to remember first if you forget everything else

If you only remember a few things, remember these:

- tables define schema
- `@DriftDatabase` registers tables
- `build_runner` regenerates code
- `select`, `into`, `update`, and `delete` handle most queries
- `where(...)` filters
- `orderBy(...)` sorts
- companion classes are for writes
- `Value(...)` controls how updates behave
- foreign keys model relationships
- schema changes may require version bumps and migrations

That small set is enough to be productive with Drift most of the time.
